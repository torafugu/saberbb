# 守備候補ログの重複キー調査

## 今回再現した原因

`player_game_fielding_candidate(game_id, count_seq, fielder_position)` の
主キーは「1試合・1球・1守備位置」の診断行を区別するためのものです。
今回確認した衝突は、既存の診断行が再初期化後も残っていたことで発生しました。

- `game_table.sql` は `DROP TABLE` → `CREATE TABLE` なので、再初期化すると試合IDを再利用します。
- 守備候補と接触診断のDDLは既存DBの更新にも使うため、`CREATE TABLE IF NOT EXISTS` です。
- 以前の `--setup` はこの2表の行を消しておらず、試合・投球・打撃ログだけが初期化されていました。
- 新しい試合が過去と同じID・球番号・守備位置を使うと、古い診断行と衝突します。

前回のGUI検証DBには、試合ID 7に対する守備候補行が837行残っていましたが、
試合ヘッダーは未実施、打撃ログは0行でした。このDBのコピーから未実施試合に
紐づく診断行だけを除去すると、837行が0行になり、423件の日程と180人の選手は
変化しませんでした。

通常イニング数そのものに起因する問題という前回の切り分けは不十分でした。
検証ハーネスにも描画ループ回数だけで待機を終える問題があったため、長い処理では
完了前に検証が先へ進む可能性がありました。待機は実時間の期限で判定し、期限を
超えた場合は明示的に失敗するよう修正しています。

## 修正

`setup_database` は、既存の試合データを再作成するトランザクション内で
`player_game_fielding_candidate` と `player_game_contact_state` も空にします。
途中でCSV読込などに失敗した場合は、診断行を含めて元のデータに戻ります。

加算用DDLは引き続き非破壊のままです。主キーも維持し、保存時の
`INSERT OR IGNORE`、上書き、生成ログの重複除去は行いません。

## 既存DBの確認と限定的な修復

次の読取SQLで、完了試合に紐づかない守備候補行を確認できます。

```sql
SELECT c.game_id, COUNT(*) AS orphan_rows
FROM player_game_fielding_candidate c
WHERE NOT EXISTS (
    SELECT 1 FROM game g
    WHERE g.id = c.game_id AND g.actual_date IS NOT NULL
)
GROUP BY c.game_id;
```

既に消し残しが発生したDBには、
[`remove_orphaned_game_diagnostics.sql`](../migrations/upgrades/remove_orphaned_game_diagnostics.sql)
を用意しています。アプリや他の書き込み処理を終了し、使用中のDBをバックアップしてから、
そのDBに対して実行します。SQLite CLIを利用する場合の例です。

```sh
sqlite3 "/実際に設定しているパス/saberbb.db" < migrations/upgrades/remove_orphaned_game_diagnostics.sql
```

このSQLは、完了試合に紐づかない守備候補・接触診断だけを削除します。
完了試合の診断、試合結果、選手、日程、打撃・投手ログ、成績テーブルは変更しません。
再実行しても同じ結果になります。既存DBを直すために `--setup` を実行する必要はありません。

完了試合へ既に混在した古い診断など、由来を判別できない行は自動削除しません。
この修復の対象は、未実施または存在しない試合に紐づく診断行です。

## 検証結果

- 修正を外すと、再初期化後も診断行が残る回帰テストが失敗します。修正後は同じキーで新しい試合の診断を保存できます。
- 初期化失敗時のロールバック、限定修復の再実行、完了試合の診断保全を含む関連62テストが成功しました。
- 固定乱数3種類のフル試合で、生成された守備候補キーの重複がなく、各行が実在する球番号へ紐づくことを確認しました。
- 問題DBのコピーを限定修復後、通常進行9試合＋分析進行9試合が成功。守備候補11,466行・接触診断1,223行を保存し、未実施試合に紐づく守備候補は0行でした。
- 新規DBでも、600選手作成から通常進行・分析進行までのGUI実イベント検証が最大12回設定で成功しました。18試合を完了し、候補ログのUNIQUE制約エラーは発生しませんでした。
