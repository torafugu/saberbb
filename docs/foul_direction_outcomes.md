# ファウル方向と最終結果の診断

`sql/diagnostics/foul_direction_outcomes.sql`を、確認したい試合IDの範囲で実行する。
既存の打撃・守備記録を読むSQLで、試合の再生成、DB移行、シミュレーターの変更は不要。

## 実行

SQLエディターで次の名前付きパラメーターを設定する。範囲は両端を含む。

- `:first_game_id`：対象試合IDの最小値
- `:last_game_id`：対象試合IDの最大値

パラメーターに対応しないエディターでは、SQL内のこの2つを実際の数値へ置換する。
1球だけ調べる場合は、両方を対象の`game_id`にして、4番目のSELECTのWHEREへ
`AND count_seq = 対象の投球番号`を追加する。LIMITより前に絞り込む。

before/afterを比較するときは、それぞれの範囲で別々に実行する。
`hla_version`は記録値を使用し、旧データのNULLは1として扱う。

## 4つの出力

1. **接触種別ごとの件数と差**：接触総数、打ち出し時のファウル方向・後方方向、最終位置のファウル方向、結果Foulの件数を比較する。
2. **全接触の遷移表**：打ち出し→初回バウンド→最終方向と、`outbound_result`、結果、捕球種別、選択経路、担当野手を集計する。件数合計は1の接触総数と一致する。
3. **差がある接触の内訳**：打ち出しがファウル方向なのに結果がFoulでない接触、および逆方向の差を全件集計する。`unknown_direction`も独立して残す。件数に上限はない。
4. **個別打球**：差がある接触を試合ID・投球番号順に先頭200件表示する。EV/VLA、角度、バウンド・フェンス時刻、捕球時刻・高さ・待機時間を確認する。全件数の判断には3を使う。

守備記録は`seq=1`のみLEFT JOINする。追加送球による二重計上と、守備記録がない接触の脱落を防ぐ。
`catch_fielder_position`が最初の捕球担当であり、追加送球後の`final_fielder_position`ではない。

## 読み方

方向ラベルは記録された角度の分類で、野球規則上の最終判定そのものではない。
`final_hla_deg`は打ち出しHLA、`polar_angle`は軌道計算の最終位置の角度で、実際の捕球位置の角度とは限らない。

| ラベル | 角度の絶対値 |
|---|---|
| fair | 45度未満 |
| foul_side | 45度以上90度未満 |
| backward | 90度以上 |
| unknown | NULL。初回バウンド角度では、バウンド記録なしも含む |

`launch_foul_directions`などの「ファウル方向」は`foul_side`と`backward`の合計。
45度ちょうども現行コードと同様にファウル側へ分類する。

特に3番目の出力で、以下を切り分ける。

- **最終方向もファウル側、DirectFly、Out**：現行コードの捕球アウト経路と整合する。捕球されたファウルフライは結果Foulには数えられない。
- **打ち出しはファウル側、最終方向はfair**：軌道上で方向が変わっている。最終結果だけから捕球ファウルとは判断しない。初回バウンド角度とフェンス衝突の有無も確認する。
- **最終方向がファウル側、BounceCatch/FinalPickup、安打・併殺など**：優先確認対象。`outbound_result`の早期終了経路も確認する。例えば`GroundRuleDouble`は最終位置のファウル判定より先に処理される。
- **守備行なし**：捕球なしファウル、場外判定による早期終了、旧データ・記録不足などを含む。守備評価が行われなかった証拠にはならない。

## 判定順と診断の限界

現行の`GameState::resolve_contact` / `resolve_ball_fielded`は次の順で処理する。

1. `outbound_result`がFoul / HomeRun / GroundRuleDoubleなら、それぞれの結果へ早期終了。
2. InFieldなら守備評価を実行。
3. `is_fly_catch`なら空中捕球処理。現在は`catch_type=DirectFly`で決まり、打撃結果はOutになる。
4. 空中捕球でなければ、`batted_ball.is_foul()`が最終位置の角度を判定。
5. 残りはフェア打球として処理。

捕球なしファウルは守備評価後でも`player_game_fielding`に捕球結果行を残さない。
また、空中捕球後のタッチアップで追加アウトが発生しても、この経路で保存する打撃結果はOutでありDoublePlayではない。
したがって、ファウル方向とFoul結果の差をすべて「捕球されたファウルフライ」と解釈しない。

`resolution_hint`はこの順序と保存値からの推定であり、実行時に記録された分岐名ではない。
捕球診断がない旧記録では確定できない経路がある。
`fly_boundary_status`はDirectFlyの時刻が記録された初回バウンド・フェンス時刻より
1e-9秒以上前かを確認する。両方の境界記録がない場合は`no_recorded_boundary`とする。
これは捕球処理の整合性確認であり、到達可能性や捕球位置がファウル側だったことの証明にはならない。

この診断は試合を再生せず、反実仮想の結果も生成しない。まず3番目の集計と、
件数の多い分類について4番目の個別例を確認して、追加記録や物理モデル変更の対象を決める。

## 検証

`python3 tests/sql/test_foul_direction_outcomes.py`

守備行なし、追加送球、方向の変化、境界角度、旧モデル、捕球時刻とイベント境界、
詳細表示上限を含むSQLiteのサンプルデータで、件数保存と分類を検証する。
